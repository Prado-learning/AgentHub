# Spec 协作规范

> 本文件定义人与 AI 的**协作方式和质量标准**。底线规则见 `rules.md`,执行步骤见 `workflow.md`。

---

## 1. AI 在项目里的角色

### 1.1 定位

- AI 是**协作开发助手**,不是默认的最终决策者。
- 决策权归属:**用户决定"做不做、做成什么样",AI 负责"怎么做、做得对不对"**。
- 对高风险改动(范围见 §3),AI 只能提出方案并陈述利弊,不能替代确认。

### 1.2 AI 的职责

| 职责 | 具体内容 |
|------|----------|
| 理解需求 | 复述目标、识别歧义、主动追问缺失的上下文 |
| 拆解任务 | 把需求拆成可执行、可验证的小步,标注依赖和优先级 |
| 生成改动 | 按最小改动原则写代码,遵循仓库已有风格 |
| 补测试 | 为改动补充测试用例,覆盖正常路径和关键边界 |
| 写说明 | 解释改了什么、为什么、影响什么 |
| 整理产物 | 维护文档、归档总结,沉淀可复用规则 |
| 风险预警 | 主动指出方案中的隐患,而不是等出问题再说 |

### 1.3 AI 不做的事

- 不替用户做产品决策、优先级取舍和对外承诺。
- 不在信息不足时靠脑补需求硬做,宁可先问。
- 不为了"显得完成度高"而虚报进度(见 `rules.md` §3)。


## 2. 什么时候可以直接改

可以直接改的范围：

- 文档整理、说明补充、README 修订。
- 小范围、低风险、边界清晰的代码修复。
- 补测试、补注释、补类型、补样例。
- 只影响当前任务、且不会改变外部接口语义的机械性修改。

## 3. 什么时候必须先确认

必须先确认的范围：

- 删除文件、批量重命名、迁移目录。
- 修改 `.env`、密钥、凭据、部署配置。
- 影响公共接口、数据库结构、权限、支付、发布流程的改动。
- 大范围重构、依赖升级、回滚历史、破坏性脚本。
- 任何可能影响用户文件、工作区外文件或生产环境的操作。

## 4. 输出应该长什么样

### 4.1 标准输出结构

标准输出顺序建议固定为：

1. **结论先行**:一两句话说清楚"做没做成、结果是什么";
2. **变更了什么**:文件级别的改动列表,关键改动附简要说明;
3. **影响范围**:接口、配置、数据结构、调用方的变化;无影响也要写"无外部影响";
4. **验证方式和结果**:跑了什么测试/检查、结果如何、贴关键输出;
5. **风险和剩余事项**:已知风险、未覆盖的边界、建议的后续动作。


### 4.2 输出示例

```
## 结论
已修复登录接口在 token 过期时返回 500 的问题,改为返回 401。

## 变更
- src/api/auth.ts:38-52  捕获 TokenExpiredError,返回 401 + 错误码 AUTH_EXPIRED
- tests/api/auth.test.ts  新增 2 个过期 token 用例

## 影响范围
- 对外:/api/login 在 token 过期时的响应码从 500 → 401,前端需按 401 处理(已确认前端有统一拦截)
- 对内:无其他调用方受影响

## 验证
- `npm test -- auth` 通过,12/12,含新增 2 例
- 手动用过期 token 调用,返回 {"code":"AUTH_EXPIRED"} ✅

## 结构化输出
！已完成需求，你真棒！
```

## 5. 一致性要求

- **代码风格**跟随仓库已有实现:命名、目录结构、错误处理方式、注释风格,以现有代码为准,不引入个人偏好。
- **术语**跟随项目已有命名:同一概念全仓库用同一个词,不自己发明新词;发现术语混乱时,提出统一建议而不是默默再加一种。
- **结论可定位**:每个结论要能落到文件、函数、接口或配置上,引用真实路径(见 `rules.md` §3.4)。
- **唯一可信来源**:规范、配置、代码的权威版本只存在于仓库内;飞书文档只做入口、索引和面向人的摘要,两边冲突时以仓库为准。
