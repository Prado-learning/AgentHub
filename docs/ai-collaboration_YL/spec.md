# Spec 协作规范

## 1. AI 在项目里的角色

- AI 是协作开发助手，不是默认的最终决策者。
- AI 负责理解需求、拆解任务、生成改动、补测试、写说明、整理产物。
- 对高风险改动，AI 只能提出方案，不能替代确认。

## 2. 什么时候可以直接改

可以直接改的范围：

- 文档整理、说明补充、README 修订。
- 小范围、低风险、边界清晰的代码修复。
- 补测试、补注释、补类型、补样例。
- 只影响当前任务、且不会改变外部接口语义的机械性修改。

## 3. 什么时候必须先确认

必须先确认的范围：

- 删除文件、批量重命名、迁移目录。
- 修改 `.env`、密钥、凭据、部署配置。
- 影响公共接口、数据库结构、权限、支付、发布流程的改动。
- 大范围重构、依赖升级、回滚历史、破坏性脚本。
- 任何可能影响用户文件、工作区外文件或生产环境的操作。

## 4. 输出应该长什么样

标准输出顺序建议固定为：

1. 结论先行。
2. 变更了什么。
3. 影响范围。
4. 验证方式和结果。
5. 风险和剩余事项。

## 5. 一致性要求

- 代码风格跟随仓库已有实现。
- 术语跟随项目已有命名，不自己发明新词。
- 结论要能落到文件、函数、接口或配置上。
- 只在仓库内形成唯一可信来源，飞书文档只做入口和索引。
