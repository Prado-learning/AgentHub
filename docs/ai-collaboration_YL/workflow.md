# Workflow 协作流程

## 1. 接收任务

- 先读需求，确认目标、边界、优先级和风险。
- 如果信息不足，先补齐上下文，再动手。

## 2. 理解现状

- 先看仓库结构、相关代码、历史记录和已有规范。
- 找到本次任务真正影响的模块，不扩大范围。
- 关注三类信息:
  - **现有 pattern**:同类问题在仓库里是怎么解决的;
  - **历史包袱**:看似奇怪的实现是否有历史原因(查 commit message 和注释);
  - **隐式依赖**:哪些地方间接依赖即将改动的代码(全局搜索调用方)。

**本阶段产出**:影响面清单——涉及哪些文件、接口、配置,以及各自当前的行为。


## 3. 拆任务

- 把任务拆成可执行的小步。
- 区分必须做、最好做、暂缓做三类。

## 4. 执行

- 按最小改动原则实现。
- 能复用现有 pattern 就复用，不额外发明结构。
- 对文档任务，优先补结构和链接；对代码任务，优先补测试和边界。

## 5. 验证

- 跑相关测试、构建或最小可复现检查。
- 记录失败原因和剩余风险，不跳过验证就宣布完成。

## 6. 总结

- 说明改了什么、为什么改、验证了什么。
- 给出仓库产物地址和飞书文档入口。

## 7. 归档

- 把可复用规则沉淀进 `spec.md`、`rules.md`、`skills/`。
- 把阶段性总结放进 `timeline.md`，方便后续继续迭代。
---

## 附 1:流程速查

```
接收任务 ──→ 理解现状 ──→ 拆任务 ──→ 执行 ──→ 验证 ──→ 总结 ──→ 归档
   │            │           │         │        │
 信息不足?    影响面     高风险步骤?  偏离计划?  验证失败?
 先澄清      最小化      先确认      先同步    如实报告
```

## 附 2:例外处理

- **紧急修复**:可压缩 §1-§3,但 §5 验证和 §6 总结不可省略;事后补齐归档。
- **探索性任务**(方案调研、可行性验证):产出从"代码改动"改为"调研结论 + 建议",仍走总结和归档。
- **任务中断**:把当前进度、未完成步骤和已知风险写入总结,保证任何人可以接着做。
