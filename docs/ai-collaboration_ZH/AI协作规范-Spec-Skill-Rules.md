# AgentHub · AI 协作规范（Spec / Skill / Rules）

> 本文件沉淀「人与 AI 协同开发 AgentHub」过程中逐步稳定下来的协作规范，作为后续迭代的统一约束。
> 项目里的大部分改动都应遵循这一套规则。建议随仓库一同维护，放在 `docs/` 目录下。

---

## 一、文档目的

在开发 AgentHub 的过程中，我们不仅完成了功能迭代，也沉淀出一套「如何与 AI 协同开发」的方法。
本规范把这套方法固化为三层约束 —— **Spec（做什么的边界）、Skill（怎么做的手法）、Rules（绝不碰的红线）** ——
让任何参与者（人或 AI）在接手任务时，都能用同样的标准判断该改什么、不该改什么、改到什么程度。

---

## 二、AI 协作能力（考察维度对齐）

本项目对「AI 协作能力」的对齐维度如下，所有协作行为都应服务于这些目标：

| 维度 | 说明 |
| --- | --- |
| 对话式协作 | 通过对话式交互完成需求创建、功能迭代和产物生成 |
| 最小化侵入 | 保持最小化修改，不破坏现有文件结构 |
| 框架尊重 | 不动 harness、agentscope 框架以及 agent 调 tool 的主逻辑 |
| 可复用沉淀 | 把协作过程沉淀成可复用的 Spec、Skill、Rules |
| 可展示性 | 让最终成果可以在飞书文档和仓库中清晰展示 |

> 评判要点：协作过程是否有清晰的目标对齐、是否尊重既有架构、是否能复用、是否可被他人快速看懂。

---

## 三、Spec —— 需求与边界约定

定义「接到一个需求时，先做什么判断」。

- 所有需求先明确目标，再决定是否改代码。
- 默认采用**最小化改动**原则。
- 新功能**优先复用**已有架构和已有产物类型（artifact / workflow / agent / tool）。
- 动手前先确认三件事：**功能是否已经存在、为什么没生效、应该改哪一层**。
- 任何涉及大改的功能，**先拆成 MVP，再考虑增强版**，不要一步到位。

---

## 四、Skill —— 协作手法

定义「真正动手时，按什么顺序、用什么方法」。

- 先读项目结构，再读关键入口，再决定改动点。
- 优先复用现有的 `conversation`、`artifact`、`agent`、`tool`、`workflow` 流程。
- **前端和后端一起看**，避免只改一边导致状态不一致。
- 修改后要做**构建或测试验证**，确认没有破坏布局或交互。
- 在出现异常时**先排查原因，不盲目改代码**（例如先看终端输出、网络请求、Git 状态，判断问题类型）。

---

## 五、Rules —— 不可逾越的红线

定义「无论需求怎么提，都不能做的事」。

- **不改文件结构。**
- **不改 harness、agentscope 框架。**
- **不改 agent 调 tool 的核心逻辑。**
- **不做大范围重构。**
- 新能力尽量**接入现有 `artifact / workflow / orchestrator` 体系**，而不是另起一套。
- 涉及不可逆操作（删除、覆盖、提交、部署）前，先讲清楚原因和影响，再执行。

---

## 六、标准协作流程（落地动作）

把上面三层约束收敛成一条可执行的流程：

1. **先对齐目标，再动手实现** —— 先讨论方案，确认无误后再改文件。
2. **先分析项目现状，再决定改动范围** —— 读结构、读入口、定位改动层。
3. **先做最小可用版本，再逐步增强** —— MVP 优先，避免一开始就贪多。
4. **遇到问题先排查，再修改** —— 解释问题成因，而不是直接给「结论式操作」。
5. **所有改动都保持对现有架构的尊重** —— 复用优先，红线不碰。

---

## 七、协作沟通约定

- 用户提需求时，应说明**目标**而非直接指定实现细节，把方案空间留给协作判断。
- AI 在执行前应**复述理解的方案与改动范围**，确认后再落地。
- 排查类任务以**解释原因**为先，不直接给"结论式操作"，便于双方建立对系统的稳定理解。
- 每一轮改动后做一次小验证（构建 / 预览 / Diff），确保过程可回溯。

---

*维护建议：每完成一个有代表性的协作阶段，回到本规范检查是否产生了新的可固化规则，并更新对应章节。*
